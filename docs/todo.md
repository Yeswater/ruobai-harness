# 会话级任务清单

## 问题

长任务里有两件事会同时坏掉：

1. **模型不知道做到哪了。** 上下文压缩后，早期计划的细节只剩摘要里的一句话；模型倾向于重新读文件、重新确认已经完成的步骤。
2. **用户不知道还要多久。** 轨迹能看每一步，但看不出“还剩几件事”。

Roadmap 里的“统一任务面板 / 任务拓扑 / 断点续跑”指向同一个需求，但 DAG 调度器会引入第二套状态机：任务状态存在内存或独立文件里，和 append-only 会话日志形成两个事实源，回放、分叉、归档都要同时维护两边。

## 方案

一个工具、一个事件、一个投影、一个面板。

### 工具 `todo_write`

- **整表替换**，不是增量。模型提交完整列表，日志里每条 `todo/updated` 都是自足的，回放不需要合并。
- 校验：≤ 40 条、每条 ≤ 400 字符、id 唯一（缺省按序号），**最多一条 `in_progress`**。
- 传空数组表示清空。
- `readOnly: true`：它只改会话自己的草稿状态，不碰外部世界，因此在 read-only 权限下也可用。

### 事件与投影

```
todo/updated { items, rev }
```

投影 `todo` 折叠为 `{ items, rev, lastSeq }`，后到的整表覆盖先前的。`rev` 单调递增，浏览器用它丢弃乱序帧。

### 系统提示

`context.registerSection` 注册 `todo` 区域，`stability: 'turn'`：它在一轮内会变，不能算进稳定前缀，也不应被工具结果裁剪影响。列表在压缩后仍在，因为每轮都会重新渲染。

另有一个静态的 `todo.guide` 区域，始终提醒「多步任务先建清单、一次只标一项进行中」：只写在工具描述里时，模型仍然把计划写成正文而不调用工具，面板始终是空的。

`maxChars` 是 6000；40 条满长度会截断。这是有意的上限——任务清单应该是短句，不是需求文档。

### 面板

`@ruobai/todo-web`：

- `GET /api/todo?sessionId=…` 返回快照；
- 收到 `todo/updated` 时通过 `ctx.ui.broadcast('todo', …)` 推送。

`ui-server.broadcast` 现在同时发出 `ui/broadcast` 事件，`web-ws` 把它转成 `{ type: 'todo', data }`，因此面板在 WebSocket 与 SSE 两条通道上都能实时更新。没有清单时不渲染任何东西；回合结束后（`session.streaming === false`）也不再渲染，避免已完成的任务清单一直占着输入区。

## 为什么不做任务依赖图

- 依赖图需要调度、重试、部分失败的状态机；这些状态一旦不落在会话日志里，回放就不可信。
- 子任务已经有 `task` 工具（本地子代理）与 `a2a`（远程 agent），它们各自有独立会话。
- 检查点提供文件级回退，`mode-goal` 提供“继续跑直到完成”。缺的只是可读的进度，而清单刚好够用。

## 失败模式

| 情况 | 行为 |
| --- | --- |
| 无会话上下文 | 工具报错，不写事件 |
| 两条 `in_progress` / 重复 id / 超长 | 工具返回错误，模型看到原因；日志不变 |
| 面板插件被卸载 | 工具与提示仍在；`GET /api/todo` 404，界面不显示清单 |
| 推送丢失 | 下次切换会话或刷新时用快照补上；`rev` 防止旧帧覆盖新帧 |
| 子代理会话 | 每个会话有自己的清单；子代理的清单不合并进父会话 |

## 验证

`packages/todo/tests/todo.spec.ts`：

- 写入后事件落日志、投影可读、系统提示包含 `<task_list>`；
- 第二次写入是替换而非合并，空数组清空；
- 两条进行中、重复 id 被拒绝且不写事件；
- HTTP 快照、缺少 `sessionId`（400）、未知会话（404）。
