# 把过程收起来：一次「过程折叠」的交互设计与实现

> 2026-10-25 · ruobai-harness
>
> 一个 agent 回合里，模型会思考、会跑命令、会读写文件。这些东西如果全部平铺，正文就会被挤到看不见；如果全部藏起来，用户又不知道它到底干了什么。这篇记录这次折叠改造的取舍：**哪些该折、什么时候折、折叠后那一行该说什么**，以及过程中踩的两个真 bug。

## 0. 起因：一屏工具卡片，正文消失

最初的转录把每个步骤都渲染成独立卡片：一条思考一张虚线框，一次工具调用一张折叠卡。单步对话很好看，多步任务就很糟：

```
🧠 思考过程   161 字 ⌄
🔧 bash  command: cd "$(git rev-parse --show-toplevel)" && pnpm build:ui …   运行中  ›
🧠 思考过程   88 字 ⌄
🔧 bash  command: git show HEAD:packages/ui-app/src/styles.css > /tmp/old.css  ›
🧠 思考过程   240 字 ⌄
…
（往下滚两屏，才是模型的回答）
```

问题不是"卡片太多"，而是**过程和结论抢同一层视觉权重**。用户来这儿是为了看结论；过程只在两种时刻有用：正在跑的时候（我需要知道它在干嘛），以及出错之后（我要看是哪一步坏了）。

于是定下两条约束：

1. **正文永远可见**，任何折叠都不能把回答藏起来；
2. **过程默认可收**，但收起时必须回答两个问题：干完了吗？花了多久？

第 2 条直接决定了架构：如果耗时是前端自己掐表算的，刷新就归零、多标签页就不一致。所以时间必须先落进会话日志。

## 1. 先让数据能回答"多久"

参考 dsh（deepseek-harness）的做法：它的 `session-stats` 投影从 `step/start` → 首个 token delta → `assistant/message` 三个事件的时间戳折出 TTFT 与解码耗时，所以翻页、压缩、重开都不影响读数。我们照这个思路，在 `message/assistant` 事件上落一份时间戳：

```ts
// packages/agent/src/index.ts
export interface StepTiming {
  stepStartTime: number
  /** 首个 text 或 reasoning delta；这一步没有流式输出时缺席。 */
  firstTokenTime?: number
  /** 组装好的消息写入日志的时刻。 */
  completedTime: number
}
```

写日志时一起带上（同一个事件里还有 `usage`，那是统计行用的）：

```ts
this.ctx.sessions.append(sessionId, 'message/assistant', {
  id: messageId,
  parts,
  at: completedTime,
  ...(stepUsage ? { usage: stepUsage } : {}),
  timing,
})
```

前端不直接读事件，读的是 `chat` 服务投影出来的 `ChatSession`。所以 `blocksOf()` 负责把一步的时间戳分发到它产出的每个块上：

```ts
// packages/chat/src/index.ts
const startedAt = timing?.stepStartTime ?? at
const finishedAt = timing?.completedTime ?? at

if (part.type === 'reasoning') blocks.push({ type: 'reasoning', text, startedAt, finishedAt })
// 工具调用是在这一步落盘之后才执行的，所以它的起点就是这一步的终点
else if (part.type === 'tool-call') blocks.push({ type: 'tool', …, startedAt: finishedAt })
```

工具的终点来自另一条事件 —— `tool/result` 的 `event.ts`。至此一行过程需要的两个边界都在数据里了：

| 行的类型 | startedAt | finishedAt |
|---|---|---|
| 思考 | 这一步的 `stepStartTime` | 正文开始流式，或整步落盘 |
| 工具 | 请求它的那一步落盘 | `tool/result` 落盘 |

**这一步的收益不只是耗时**：刷新页面后行尾还是 `12s`，不是我另存了一份内存状态。

## 2. 折叠的边界：正文切分过程

分组逻辑只有一条规则：**遇到正文就断组**。所以"思考→命令→命令→思考→正文→命令"会变成「一个过程组 + 正文 + 另一个过程组」。这样折叠永远不会跨越正文，用户读到的顺序和模型实际执行的顺序一致。

连续的工具步骤会被合并进同一个组（它们本来就是同一次"动作爆发"），不需要用户逐张展开。整段逻辑是个纯函数，没有 React：

```ts
// packages/ui-app/src/transcript-model.ts
export function buildPlan(messages: ChatMessage[]): PlanItem[] {
  const plan: PlanItem[] = []
  let group: ProcessItem[] = []

  for (const message of messages) {
    if (message.role === 'user') { flush(); plan.push({ kind: 'user', … }); continue }
    if (message.status === 'streaming' && message.blocks.length === 0) {
      flush(); plan.push({ kind: 'pending', … }); continue   // 「思考中…」占位
    }

    message.blocks.forEach((block, index) => {
      if (block.type === 'text') { flush(); plan.push({ kind: 'text', … }); return }
      if (block.type !== 'reasoning' && block.type !== 'tool') return
      group.push(…)                                          // 累积到当前组
    })
  }
  flush()
  return plan
}
```

`flush()` 就是那条规则：任何非过程块出现，当前组结束。

## 3. 三个状态，优先级写死

一个过程组只有三种可见状态：

| 状态 | 组头文字 | 谁决定 |
|---|---|---|
| 运行中 | `执行中…` + 旋转/呼吸的图标 | 组内有 `pending` 的行 |
| 已完成 | `已完成，用时 1分30秒` | 组内全都结束 |
| 用户覆盖 | 同上一行，但保持用户点选的开合 | 用户点击 |

难点在"自动展开/自动收起"和"用户点过"会互相打架：用户正在读一个已结束的组，下一批工具开始跑，如果无脑自动展开，阅读位置就被打乱；反过来，用户手动收起一个正在跑的组，又被自动展开，等于点了没用。

做法是一个三态变量，`null` 表示"跟随运行状态"：

```tsx
function ProcessGroup({ items, streaming }: { items: ProcessItem[]; streaming: boolean }) {
  const running = streaming && isGroupRunning(items)
  // null = 跟随运行状态；true/false = 用户显式选择
  const [override, setOverride] = useState<boolean | null>(null)
  const open = override ?? running

  useEffect(() => {
    // 有新动作开始 → 丢弃旧的覆盖，重新跟随
    if (running) setOverride(null)
  }, [running, items.length])
```

用户点开一个已完成的组，`override = true`；这一组不会再自己收起。直到**下一批工具开始执行**，`running` 变 true，覆盖被清空，自动展开重新接管。规则只有一句：**运行状态优先，用户选择在位期间优先于自动收起**。

## 4. 折叠后那一行该说什么

第一版试过把整批工具汇总成一句：「运行 3 条命令，读取 5 个文件，编辑 1 个文件」。信息密度不错，但用户看不出**具体跑了什么** —— 而这恰恰是让人愿意点开的原因。

参考截图里的做法改成逐行「动作 · 对象」，折叠头只留一句「已完成，用时 X」：

```
已完成，用时 1分30秒 ⌄
```

展开后：

```
  🧠 思考 · The last command had an AssertionError in one of the Pyt…   7s
  🔧 运行命令 · Fix final review items and rerun demo                  12s
  🔧 运行命令 · pnpm --filter docs test ↑                              9s
     $ pnpm --filter docs test
     ✓ 12 passed
     ✗ 1 failed  README line 3
  🧠 思考 · The content didn't apply; the README line 3 still says …     4s
```

标签来自工具名到人话的映射，内部的工具 id 不外露：

```ts
// packages/ui-app/src/tool-summary.ts
const BUCKETS: Bucket[] = [
  { row: '运行命令', names: ['bash', 'run_command', 'shell', 'execute_command'] },
  { row: '调用子智能体', names: ['task', 'delegate', 'subagent'] },
  { row: '读取文件', names: ['read_file', 'read', 'view_file'] },
  { row: '创建文件', names: ['write_file', 'create_file', 'write'] },
  { row: '编辑文件', names: ['edit_file', 'apply_patch', 'edit', 'multi_edit'] },
  { row: '查看目录', names: ['list_dir', 'list_files', 'list_directory'] },
  { row: '搜索', names: ['search_files', 'grep', 'glob', 'search'] },
]
```

点后面的摘要按类型取：命令取第一行（90 字符截断），文件取路径，子智能体取任务描述。MCP / A2A 那些 `mcp__server__tool` 统一落到「其他操作」——它们本来就没有通用语义。

耗时格式化只保留两级，够用且不啰嗦：

```ts
export function formatDuration(ms: number): string {
  const seconds = Math.max(0, Math.round(ms / 1000))
  if (seconds < 60) return `${seconds} 秒`
  const minutes = Math.floor(seconds / 60)
  if (minutes < 60) return `${minutes}分${seconds % 60 ? `${seconds % 60}秒` : ''}`
  const hours = Math.floor(minutes / 60)
  return `${hours}小时${minutes % 60 ? `${minutes % 60}分` : ''}`
}
```

行级耗时是另一套口径（`12s`，低于 1 秒不显示）—— 组头回答"这一批花了多久"，行尾回答"这一步花了多久"，尺度不同，格式就不该一样。

## 5. 两个 bug，都出在「状态靠猜」

### bug 1：回合结束了，行里还写「思考中」

第一版判断一行是否在跑，只看它自己的 `finishedAt`：

```ts
// 错的写法
const pending = block.finishedAt === undefined
```

看着合理，实际是**用"有没有时间戳"去推断"有没有结束"**。这两个命题只在"日志一定有时间戳"时等价。而历史会话没有时间戳 —— 于是每个思考行永久停在「思考中」，即使这个回合半小时前就结束了。

真正权威的信号在上一层：**消息自己是否还 `streaming`**。消息已经结束，它产出的块必然也结束了：

```ts
// 现在的写法
const settled = message.status !== 'streaming'
const pending = settled
  ? false
  : block.type === 'reasoning' ? block.finishedAt === undefined : isRunning(block)
```

顺带把判定从视图搬进了 `buildPlan`：视图只渲染 `pending`，不再自己猜。`ProcessGroup` 还额外要求 `session.streaming` 才认为自己在跑，防止一条没有时间戳的旧数据把整个组挂成"执行中"。

### bug 2：正文已经在流，思考行还写「思考中」

`finishedAt` 原来只来自整步落盘（`completedTime`）。但模型的典型节奏是：先吐一段思考，紧接着开始输出正文。正文都流了两秒了，思考那行的 `finishedAt` 还是 `undefined`，界面就一直写「思考中」。

修法是在数据产生的地方打点：正文第一个 delta 到达，说明上一块思考结束了。

```ts
// packages/chat/src/index.ts
ctx.on('agent/delta', (id, messageId, delta) => {
  const now = Date.now()
  // 正文开始 → 前面的思考已经结束
  closeReasoning(message.blocks, now)
  …
})
```

落盘时再对齐一次，取更早的边界（实时打点比整步落盘更贴近真实）：

```ts
function keepEarlier(current?: number, fallback?: number) {
  if (current === undefined) return fallback
  if (fallback === undefined) return current
  return Math.min(current, fallback)
}
```

两条教训其实是同一条：**能表达"结束"的字段，必须是"结束"本身，而不是"结束时会顺带产生的某个东西"**。前者缺失就是数据缺失，后者缺失会被误读成"还在跑"。

## 6. 样式：一行 28px 的灰字

视觉上不做什么花活，靠对齐和层级：

- 行高 28px（`padding: 4px 0` + `line-height: 1.6`），`align-items: baseline` —— 图标、标签、摘要、耗时四段文字共用一条基线，图标单独 `align-self: center`；
- 标签（`运行命令`）用 `--faint`，摘要用 `--muted`，耗时用等宽字体 `10.5px`。层级靠色阶，不靠字重；
- 折叠头箭头是最后一个 `svg`，收起 `rotate(-90deg)`、展开 `rotate(0)`，0.15s 过渡；
- 展开体不用卡片，只用左侧 2px 竖线 + 半透明底：它属于某一行，不该长成独立容器；
- 组的上下留白 `margin: -8px 0`，比转录默认节奏更紧 —— 折叠起来的一段过程应该贴着它所属的段落，而不是自己占一块。

结构上没用 `<details>/<summary>`：`open` 是受控的、要同时受"运行状态 + 用户点击"两个输入影响，还要在收起时**不渲染** body（多步任务的 body 可能上千行 DOM）。`<button aria-expanded>` + 条件渲染更直接，键盘和读屏也照常。

## 7. 怎么测

三层，各自解决不同的问题：

**模型层（纯函数，快）** —— `transcript-model.spec.ts`、`tool-summary.spec.ts`：

- 分组：连续工具步骤并进一组；正文/思考打断后重新开组；plan 的 key 唯一。
- 状态：`pending` 只在未结束的步骤里为真；**已结束的步骤即使没有时间戳也不得 pending**（bug 1 的回归）。
- 耗时：`groupDuration` 取最早开始到最晚结束；缺任一边界返回 `undefined` 而不是 0；`formatDuration` 的边界（0 秒 / 42 秒 / 1分30秒 / 2分 / 1小时5分）。

**衔接层（集成）** —— `chat.spec.ts` 里直接断言实时投影：

```ts
// 正文开始流式的那一刻抓一次投影：这正是以前会写「思考中」的状态
const midTurn = await live
expect(reasoning.startedAt).toBeTypeOf('number')
expect(reasoning.finishedAt).toBeTypeOf('number')
// 落盘后边界不被拉宽
expect(settled.finishedAt).toBe(reasoning.finishedAt)
```

**几何（一次性）** —— 折叠这类布局问题，单测测不出来。用真实 `styles.css` 起一个静态样稿，headless Chrome 量 `getBoundingClientRect`：行高 28px、箭头紧贴标题（不是被 flex 推到最右）、展开体在行正下方。

## 8. 已知取舍

- **旧会话没有时间戳**，组头只能显示「已完成」而不是「已完成，用时 X」。这是可接受的降级：能做的不该是编一个数字。
- **行级耗时低于 1 秒不显示**。`<1s` 的噪声比信息多，宁可留白。
- **思考行的摘要是首行截断**，不是摘要生成 —— 不额外调用模型，代价是长思考看起来会断在半句。
- **一个组只报失败数**（`已完成，用时 2 秒（1 个失败）`），不报成功数。成功是默认值，除非它值得注意，否则不占字。
- **子智能体的内部步骤不在这一层**：它们是独立会话，折叠只覆盖当前会话可见的动作。

## 9. 复盘

三句话：

1. **能折的是过程，不能折的是结论。** 判断标准不是"内容多不多"，而是"用户来这儿是不是为了它"。
2. **状态由数据决定，不由视图猜。** 一行在不在跑，要么问它自己（时间戳齐全时），要么问它的上一层（消息/回合是否结束）；视图只负责画。
3. **耗时来自日志，不来自内存。** 一切会消失的读数，最后都会变成"刷新一下就不一样了"的 bug。

改动落在这些地方：
