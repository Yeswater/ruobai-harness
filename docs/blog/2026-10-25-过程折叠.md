# 把过程收起来：agent 回合的过程折叠

> 2026-10-25 · ruobai-harness
>
> 一个回合里，模型会思考、跑命令、读写文件。全平铺会把正文挤出屏幕，全藏起来又看不出它干了什么。这篇讲折叠的判定规则：**哪些折、何时折、折起来那一行说什么**。

## 两条约束

过程和结论不该占同一层视觉权重。过程只在两种时刻有用：正在跑（它在干嘛）、出错之后（哪一步坏了）。由此定下：

1. **正文永远可见** —— 任何折叠都不能把回答藏起来；
2. **过程可收，但收起后要回答**：干完了吗、花了多久。

第 2 条决定了架构：耗时若由前端掐表，刷新就归零、多标签页会不一致。**时间必须先落进会话日志。**

## 时间从哪里来

参考 dsh 的 `session-stats` 投影：从 `step/start` → 首个 token → `assistant/message` 三个事件的时间戳折出 TTFT 与解码耗时，所以翻页、压缩、重开都不影响读数。沿用这个口径，每步在落盘时带一份时间戳：

```ts
export interface StepTiming {
  stepStartTime: number
  firstTokenTime?: number   // 首个 text 或 reasoning delta
  completedTime: number     // 消息写入日志
}
```

`chat` 投影把这组边界分发到该步产出的每个块上：

```ts
if (part.type === 'reasoning') push({ type: 'reasoning', startedAt: stepStartTime, finishedAt: completedTime })
// 工具是在这一步落盘之后才执行的，起点即这一步的终点
else if (part.type === 'tool-call') push({ type: 'tool', startedAt: completedTime })
```

工具的终点来自 `tool/result` 的 `event.ts`。于是：

| 行 | startedAt | finishedAt |
|---|---|---|
| 思考 | 该步 `stepStartTime` | 正文开始流式，或整步落盘 |
| 工具 | 请求它的那一步落盘 | `tool/result` 落盘 |

收益不只是耗时：刷新后行尾还是 `12s`，没有第二份内存状态。

## 折叠边界：正文切分过程

规则只有一条：**遇到正文就断组**。"思考→命令→命令→思考→正文→命令"变成「组 + 正文 + 组」，折叠不会跨越正文，读到顺序与执行顺序一致。

`buildPlan` 是纯函数，视图只做渲染：

```ts
for (const message of messages) {
  if (message.role === 'user') { flush(); push({ kind: 'user' }); continue }

  for (const block of message.blocks) {
    if (block.type === 'text') { flush(); push({ kind: 'text' }); continue }
    if (block.type === 'reasoning' || block.type === 'tool') group.push(toProcessItem(block))
  }
}
```

## 三个状态

| 状态 | 组头 | 谁决定 |
|---|---|---|
| 运行中 | `执行中…` + 呼吸图标 | 组内有 pending 的行 |
| 已完成 | `已完成，用时 1分30秒` | 组内全部结束 |
| 用户覆盖 | 同上，保持用户点选 | 用户点击 |

自动开合与用户点击会互相打架：读着已结束的组，下一批工具开跑，无脑展开会打乱阅读位置；手动收起正在跑的组，又被自动展开，等于没点。用一个三态变量解决，`null` 表示"跟随运行状态"：

```tsx
const running = streaming && isGroupRunning(items)
const [override, setOverride] = useState<boolean | null>(null)
const open = override ?? running

useEffect(() => { if (running) setOverride(null) }, [running, items.length])
```

用户点开一个已完成的组，它就不再自己收起；直到**下一批动作开始**，覆盖被清空，自动展开重新接管。

### 空步骤不能另起一行

早期的实现里，"这一步还没产出"是一个独立的 `pending` 计划项，渲染成正文下方的一行「思考中…」。结果是每轮工具往返都让 plan 结构在「已完成的组」和「思考中…」之间切换，DOM 重建、滚动跳动。

现在空步骤只是**当前组的一个标记**，复用同一个 group key，在组内部渲染一行等待：

```ts
if (message.blocks.length === 0) {
  if (message.status === 'streaming') { open(`${message.id}-pending`); waiting = true }
  continue
}
// flush 时：有行就是普通组，没行就是 placeholder
plan.push({ kind: 'process', key: groupKey, items: group, ...(group.length ? {} : { placeholder: true }) })
```

一个回合的多步执行因此始终是**一个连续的组**，只有正文会把它切开。

## 折起来那一行说什么

把整批工具汇总成一句「运行 3 条命令，读取 5 个文件」密度不错，但看不出具体做了什么，而那正是让人愿意点开的东西。改用逐行「动作 · 对象」，组头只留一句状态：

```
已完成，用时 1分30秒 ⌄
  🧠 思考 · The last command had an AssertionError in one of the Pyt…   7s
  🔧 运行命令 · Fix final review items and rerun demo                  12s
  🔧 运行命令 · pnpm --filter docs test                                9s
     $ pnpm --filter docs test
     ✗ 1 failed  README line 3
```

标签来自工具名到人话的映射，内部 id 不外露；摘要按类型取：命令取首行（90 字符截断）、文件取路径、子智能体取任务描述。MCP / A2A 的 `mcp__server__tool` 统一落到「其他操作」——它们没有通用语义。

耗时有两套口径：组头回答"这一批花了多久"（`1分30秒`），行尾回答"这一步花了多久"（`12s`，不足 1 秒不显示）。尺度不同，格式就该不同；整组不足 500ms 时组头只写「已完成」，不打印「用时 0 秒」。

## 三个坑，都是"状态靠猜"

**① 只看块自己的 `finishedAt`**。用"有没有时间戳"推断"有没有结束"，只在日志必然带时间戳时成立。历史会话没有时间戳，于是每个思考行永久停在「思考中」。权威信号在上一层——消息是否还 `streaming`：

```ts
const settled = message.status !== 'streaming'
const pending = settled ? false : (block.finishedAt === undefined)
```

判定也随之从视图搬进 `buildPlan`，视图只渲染 `pending`。

**② 结束时间来得太晚**。`finishedAt` 原本只来自整步落盘，而模型的典型节奏是先吐思考、紧接着输出正文：正文都流了两秒，思考行仍写「思考中」。修法是在数据产生处打点——正文第一个 delta 到达即关闭前一块思考，落盘时取更早的边界：

```ts
ctx.on('agent/delta', (id, messageId, delta) => { closeReasoning(message.blocks, Date.now()); … })
```

**③ 被中断的动作没有结尾**。停止回合或工具被取消时，动作没有 `finishedAt`，整组的 `end` 就成了 `undefined`，组头退化成「已完成」，用时消失。两处兜底：回合结束时把仍然开着的块统一封口（`finishedAt ??= now`）；取边界时允许用 `startedAt` 代替缺失的 `finishedAt`。

三条其实是同一条：**能表达"结束"的字段必须是"结束"本身**。它缺失只是数据缺失；换成"结束时会顺带产生的某样东西"，缺失就会被误读成"还在跑"。

## 样式与实现取舍

- 行高 28px，`align-items: baseline` 让图标、标签、摘要、耗时共用一条基线，图标单独居中。
- 层级靠色阶（标签 `--faint`、摘要 `--muted`、耗时等宽 10.5px），不靠字重。
- 展开体不用卡片：左侧 2px 竖线 + 半透明底，它属于某一行，不该长成独立容器。
- 组的上下留白比转录默认节奏更紧，折叠起来的一段过程应贴着所属段落。
- 没用 `<details>/<summary>`：`open` 要同时受"运行状态 + 用户点击"控制，收起时还要**不渲染** body（多步任务的 body 可达上千行 DOM）。`<button aria-expanded>` + 条件渲染更直接，键盘与读屏照常。

## 怎么测

- **模型层**（纯函数）：分组边界、`pending` 只在未结束步骤为真、空步骤并入当前组而非另起一项、组耗时取最早开始到最晚结束、缺边界时的退化、耗时格式的边界值。
- **衔接层**（集成）：正文开始流式的那一刻抓投影，断言思考块已有结束时间，且落盘后边界不被拉宽；回合被停止后所有块都被封口。
- **几何**（一次性）：折叠属布局问题，单测测不出来。用真实 `styles.css` 起静态样稿，headless Chrome 量 `getBoundingClientRect`。

## 已知取舍

- 历史会话若完全没有时间戳，组头只能写「已完成」——不编数字。
- 行级耗时不足 1 秒不显示：`<1s` 的噪声比信息多。
- 思考行摘要是首行截断而非生成摘要：不额外调模型，代价是长思考断在半句。
- 只报失败数（`已完成，用时 2 秒（1 个失败）`），不报成功数——成功是默认值。
- 子智能体的内部步骤不在这一层：它们是独立会话。

## 三句话

1. **能折的是过程，不能折的是结论。** 标准不是"内容多不多"，而是"用户来这儿是不是为了它"。
2. **状态由数据决定，不由视图猜。** 一行在不在跑，要么问它自己，要么问它的上一层。
3. **耗时来自日志，不来自内存。** 会消失的读数，最后都会变成"刷新一下就不一样"的 bug。
