# 让沙箱先通过它自己

> 2026-10-26 · ruobai-harness
>
> 给 agent 上 macOS Seatbelt 的过程里，最难的不是写规则，而是判断一条规则**到底有没有生效**。这篇不按时间顺序复盘，只留下几条后来反复用到的判断：沙箱如何以三种方式失败、内核只认哪些事实、以及为什么“能解释自己的边界”比“更厚的墙”更重要。

## 一条配置正确的规则，如何让所有命令起不来

最早的一版网络白名单长这样：

```sbpl
(allow network-outbound (remote ip "registry.npmmirror.com:443"))
```

语法合法，策略 IR 正确，status 面板也显示“网络：allowlist”。但任何命令一执行，`sandbox-exec` 就在应用 profile 的阶段退出：

```
sandbox-exec: host must be * or localhost in network address
```

`sandbox-exec` 对网络地址过滤器只接受 `*` 和 `localhost`。域名不行，IPv4 字面量不行，`remote tcp` 也不行。把域名解析成 A 记录再写进去，只会让结果从“规则不匹配”变成“整份 profile 无法应用”——**每一条命令都起不来**。

这类失败比“配置太松”更值得写进设计：安全配置有三种状态，而我们通常只检查前两种。

| 状态 | 表现 | 危险程度 |
|---|---|---|
| 生效 | 规则按预期拦截或放行 | — |
| 明确拒绝 | 配置错误，启动失败/命令失败 | 高，但可见 |
| **假生效** | 面板显示已配置，实际规则不匹配或整份失效 | 最高 |

“假生效”是所有安全配置里最昂贵的错误：它让使用者停止怀疑。修法不是再加一层 try/catch，而是承认一个前提——**配置的正确性必须由测量证明，不能由解析器证明**。

后来这条原则变成了 provider 的硬约束：编译前先确认每条网络规则能被这台 macOS 表达；不能表达的条目告警并跳过（fail-closed，但 profile 仍可运行），可执行的规则才写进 profile。跳过一条规则，等于少了一条放行；保留一条无效规则，等于整份沙箱不存在。

## 沙箱的三种失败

把实测里遇到的所有问题归类，其实只有三种：

| 失败 | 症状 | 设计回应 |
|---|---|---|
| 太松 | 守卫被绕过、写根被放大、环境变量泄漏 | 最小豁免、可写⟹可读、`env` 清洗 |
| 太紧 | 管道不能 fork、测试 runner 杀不掉 worker、DNS 解析不了 | 基线能力（fork/signal/ioctl/mDNS）与真实工具链回归 |
| 假生效 | profile 无法应用、规则永不匹配、自检只测了 `echo` | 可应用性预检、结构化 denial、真实命令自检 |

社区讨论沙箱时，注意力通常在“太松”。但对一个每天要跑 `git`、`npx`、`vitest` 的 harness，**“太紧”会立刻毁掉可用性**，而“假生效”会同时毁掉可用性和安全感。三者必须一起设计。

一个具体的例子：`(deny default)` 下不写 `(allow process-fork)`，`sh -c 'cmd'` 会退化成直接 exec，`echo hi` 依然成功；直到第一条管道、第一个 `&&` 或任何启动 helper 的工具才暴露。它骗过了“单命令烟测”，也骗过了自检。

所以“沙箱可用”的判据不能是“跑通一条命令”，而是一组**形态各异的真实命令**：管道、子 shell、`git`、`npx`、测试 runner、超时清理。缺一个，就有一类边界没被验证。

## 内核只认事实

Seatbelt 不是策略解释器，它只执行内核事实。下面这些结论都不是来自文档，而是本机反复测量的结果：

| 事实 | 设计后果 |
|---|---|
| `deny` 无条件压过 `allow`，与顺序、具体程度无关 | “审批通过后追加一条 allow”行不通，只能删掉命中的 deny、重新编译 |
| 判定按 realpath 后的 vnode | `/var` 与 `/private/var`、`/usr/local/bin/git -> /usr/local/git/bin/git` 都必须展开 |
| 子进程对网络拒绝**完全无痕** | 归因只能靠内核统一日志；`curl` 的 exit 7 只是启发式 |
| 拒绝日志里混着 `logd_helper` 等无关进程 | 归因必须按 pid 过滤，否则状态面板会被噪音淹没 |
| `env` 不受沙箱约束 | `echo $RBU_TOKEN` 能直接拿到宿主令牌，必须在 spawn 前清洗 |
| `signal` 的 `self`/`others` 都不能给子进程发信号，`children` 可以 | 没有它，任何测试 runner、超时 supervisor 都活不下来 |
| `/dev/dtracehelper` 的启动探测是 **ioctl**，不是 read/write | 只放行 `file-read*`/`file-write*` 时，每条命令都会留下一条假拒绝 |
| 沙箱内 DNS 是到 mDNSResponder 的 unix socket 出站 | 只放行 `*:443` 仍解析不了域名，必须单独放行这条 socket |

这些事实组合起来指向同一个结论：**策略必须是数据，profile 必须是每次编译的产物**。静态 `.sb` 文件只能承载与策略无关的基线；凡是与工作区、守卫、网络授权有关的部分，都要在运行时生成，并经过一次真实执行来验证。

我们的 profile 不落盘，通过 fd 3 传给 `sandbox-exec`：

```ts
const child = spawn('/usr/bin/sandbox-exec', ['-f', '/dev/fd/3', '/bin/sh', '-c', command], {
  stdio: ['ignore', 'pipe', 'pipe', 'pipe'],
  detached: true,
})
// profile 从父进程写入 fd 3：不落 /tmp，不出现在 ps 里
```

这既是安全考虑（沙箱内的进程读不到自己的边界），也是工程考虑（profile 的版本与策略版本天然一致）。

## 用不变式替代白名单

第一版 exec 白名单是枚举式的：`/usr/bin`、`/bin`、`/usr/local/bin`……然后一个接一个地修：nvm 的 `node` 不在里面，`npx` 是符号链接，esbuild 的 native binary 在 pnpm 的 `.pnpm` 存储里。每修一个，就多一条“工具链特例”。这不是配置问题，是模型错了。

node 生态里，**能写的地方本来就能放脚本**。拒绝执行只能挡住工具链，挡不住 `sh dropped.sh` 或 `node -e`。真正的边界是写授权与一组明确的危险可执行文件，而不是把所有可执行文件列一遍。

于是规则换成两条不变式：

> **可写 ⟹ 可执行**：给了写权限，就同时给 exec。
> **可写 ⟹ 可读**：写到 TMPDIR 的文件必须能读回。

```ts
const execPaths = [
  ...BASELINE_EXEC,
  ...options.execAllowPaths,
  ...policy.exec.allowPaths,
  ...policy.fs.write.map(grant => grant.path), // 可写即放行
]
```

硬边界因此收缩到可审计的少量条目：`security`、`osascript`、`sudo`、`su`、`launchctl`、`crontab`、`setsid`、`nohup`。这些不是“白名单的例外”，而是“写授权也不该覆盖的能力”。

不变式的好处不是更松，而是**可推理**：看到一条写授权，就知道它的全部含义；看到一个拒绝，就知道它为什么是边界。枚举白名单则相反——每加一个特例，边界就更模糊一层。

## 拒绝之后，边界必须能说话

沙箱在操作系统层面阻断操作后，最坏的结果不是失败，而是 agent 开始重试：换路径、加 `sudo`、改用 `python -c`。它不知道自己撞上了墙，只知道命令不工作。

所以拒绝必须被**分类、归因、交回模型**：

```
sandbox-exec 拒绝
  → exit code / stderr / 内核日志 / 命令文本（四路证据）
  → Denial { kind, target, guard, evidence, confidence }
  → Escalation.plan：可放宽吗？放宽到哪一层？
  → approval.request（只在边界真正被触发时）
  → allow：用最小豁免重跑一次；deny：结构化拒绝回到模型
```

三个约束让这条链路不变成“每步弹窗”：

1. **只在硬边界实际触发时升级**。正常命令零提示；成功命令里混进的启动探测被当作噪音过滤。
2. **豁免单位必须与拒绝单位一致**。拒绝发生在文件上，豁免就是 `write-file` 单文件；用 `dirname()` 会把“一个文件”放大成整个 `/dev`。
3. **有些边界永不放宽**。网络、进程控制、mach 服务、AppleEvent 不在人的“一次性授权”范围内；它们需要另一种信任模型。

超时也必须 fail-closed：审批请求有 deadline，`onTimeout` 只有 `deny` 一个字面量。一个“没人应答就放行”的审批不是防线。

最后，拒绝要以模型能理解的形式写回：

```
[sandbox] 操作被 macOS Seatbelt 拒绝（不是文件权限不足，sudo 无效）
kind: fs-write-guarded
guard: git-dir
target: …/.git/config
请勿重试同一操作；如需该资源，请让用户把它复制进工作区或显式放宽策略。
```

这句话不是 UI 文案，是控制流的一部分。

## 边界由插件组合，而不是一个 if

沙箱最终被拆成一条职责清晰的插件链，每个只做一件事：

| 插件 | 职责 |
|---|---|
| `sandbox` | provider 表与 run 登记；卸载时先 abort 全部 run 再 destroy |
| `sandbox-policy` | 策略 IR、守卫表、`check()` |
| `sandbox-guards` | `.git`/`.ssh`/`.env`/LaunchAgents 等默认守卫 |
| `sandbox-macos` | SBPL 编译、`sandbox-exec` 执行、自检 |
| `sandbox-denial` | 拒绝分类、指纹、重复检测 |
| `sandbox-native-log` | `log stream` 归因探针（子进程本身也是要回收的资源） |
| `sandbox-escalation` + `approval` | 从不放宽到审批，再到最小豁免重跑 |

拆分的收益不是“看起来模块化”，而是三条真实约束：

- **依赖不能成环**。沙箱核心不 `inject` 审批；审批也不 `inject` 沙箱。中间隔出 `denial` 与 `escalation`，两个 fiber 才能各自热重载。
- **卸载必须可逆**。profile 缓存、provider 表、run 登记、日志探针，全部通过 `ctx.effect` 交出 disposer。热卸载时先摘表、再 abort、再 destroy；否则“卸载沙箱”反而会留下一批在旧 profile 下运行的孤儿进程。
- **进程内工具是第二条防线**。bash 沙箱管不到 `write_file`/`read_file`，所以 `tool-fs` 必须查同一个 `sandboxPolicy.check()`；否则 `.git`/`.ssh` 只挡得住 shell。

有一件事故意没有做成插件：审批超时的 fail-closed 行为放在内核。因为“删掉一个插件就能打开超时后放行”等于防线不存在。

## 沙箱必须能通过它自己

`cordis.yml` 把 harness 自己的 shell 换成 `shell-sandboxed` 之后，agent 的每条命令都开始经过自己写的沙箱。这是最好的一次测试，也是最危险的一次：**沙箱出问题时，它第一个切断的是验证通道**。

没有 `process-fork` 时，连 `cmd > file` 都失败，无法用 shell 合并日志；没有 exec 白名单里的 node 根目录时，`npx tsc` 起不来；profile 无法应用时，所有命令一起 exit 65。你没法用被沙箱困住的 shell 去修沙箱。

后来固定下来两条工程约束：

1. **永远保留一个不经过沙箱的执行器**（`shell-direct`），切换是 `cordis.yml` 一行。它不是后门，是逃生舱。
2. **自检必须跑真实命令**，而不是 `echo hi`。管道、`&&`、`git status`、`npx tsc`、`vitest`、超时清理，一样不能少。任何一条失败，都说明有一类边界没被真正验证。

再往前一步，是让沙箱**展示自己**：provider、profile digest、守卫清单、拒绝时间线、会话级升级开关。它们被放进设置页与上下文右栏，而不是散落在日志里。一个无法被观察的边界，最终一定会被当成“网络坏了”或“工具出问题了”。

## 结语

回头看，沙箱的难点从来不是“写一条 deny 规则”。真正的难点是：

- 区分“规则正确”与“规则生效”；
- 区分“安全”与“可用”，并接受两者都必须在真实命令上验证；
- 把拒绝变成一种**可解释、可升级、可回收**的事件；
- 在沙箱接管 shell 之后，仍然保留一条能修它的通道。

边界不是一份 profile 文件，而是四样东西的合集：**测量过的事实、可推理的不变式、明确的失败语义、以及可观察的运行状态。** 缺一样，墙看起来还在，但门已经开了。
