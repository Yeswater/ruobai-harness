# 记住与知道：长期记忆和 LLM Wiki 的分工

> 2026-10-28 · ruobai-harness
>
> 记忆解决“每次都在场”，wiki 解决“需要时找得到”。这两件事看起来都叫“知识”，失败方式却完全不同，因此不能塞进同一个库：前者必须可裁剪、可衰减；后者必须可检索、可溯源、可审核。本文讲这套两层设计怎么来的、哪些地方故意不自动化，以及代价是什么。

## 一、先分清两种失败

一个 agent 的“知识”通常会被做成一个向量库：把对话、文档、结论都切块，检索 top-k 注入。这个方案最诱人的地方是统一，最容易出问题的地方也是统一——它分不清两种完全不同的需求：

- **必须每次都在场的东西**：用户偏好、项目约束、已确认的决策、踩过的坑。它们不该靠“这次检索有没有命中”来决定是否出现。
- **需要时才查的东西**：架构说明、调研结论、SOP、术语、来源摘录。它们不该每轮都占用上下文，也不该因为一次写入就永久生效。

前者的失败是**该在的时候不在**：被预算裁掉、被新事实取代、scope 落错。后者的失败是**找的时候找不到，或者找到的是过期版本**。

我们的分法因此不是按大小，而是按失效方式：

| | 长期记忆 | LLM Wiki |
| --- | --- | --- |
| 目标 | 每次请求都出现 | 需要时检索得到 |
| 注入 | 每轮注入，硬预算 ≤ 2k tokens | 只常驻目录（≤ 1,200 字符），正文按需读 |
| 存储 | append-only journal，编译成稳定快照 | Markdown 页面，索引是可重建的派生物 |
| 写入 | 用户命令 / 可选蒸馏 | 用户命令、模型提案、审批后的写入 |
| 主要失败 | 被裁、过期、scope 错 | 检索不到、来源过期、冲突未消解 |

第一行就能推出后面的所有取舍。记忆既然每轮都发，它的核心指标就不是“存得多”，而是“**预算内最该出现的有没有出现**”。wiki 既然按需读，它的核心指标就不是“索引有多聪明”，而是“**找到的结论能不能被引用**”。

## 二、记忆：可裁剪的常驻内容

记忆的事实来源是一条只追加的 journal。会话结束、用户执行 `/remember`、或者蒸馏插件运行，写入的都是事件；`MEMORY.md` 和注入块由 journal 确定性编译而来。同一份 journal 必须得到逐字节相同的文件——这不是洁癖，而是因为注入块位于 system prompt 的固定位置，动态排序会直接让前缀缓存失效。

“确定性”还带来一个更重要的约束：**排序不能看热度**。按 `lastUsedAt`、置信度或命中次数动态重排，会让同样的日志在不同会话渲染出不同字节。所以我们固定按 `scope → kind → hash(id)` 排序，衰减也只改变“是否有效”，不改变有效条目的顺序。

注入预算分三层：

| 范围 | 预算 |
| --- | ---: |
| global | ≤ 800 tokens |
| project | ≤ 1,200 tokens |
| 合计硬上限 | 2,000 tokens |

超预算时按固定优先级裁剪：`pinned` → `constraint` / `decision` → `preference` → `fact` / `gotcha` / `procedure` → 最旧。被裁掉的条目不是消失，仍然可以 `memory_search`。

这里有一个容易被忽略的判断：**规则不要写进记忆**。记忆会被预算裁剪，而“提交信息用中文摘要”这类规则一旦被裁，模型下一轮就可能不遵守。必须每次生效的规则属于 `AGENTS.md` 或系统提示，不属于会被预算管理的记忆。

### 自动蒸馏为什么默认不开

`memory-distill` 可以在回合结束或空闲时抽取向、约束与决策，但默认是 `rules` 模式：只做确定性抽取，零 LLM 调用。LLM 模式需要显式开启，并且有四道闸：

- 输入只取用户消息、助手最终回复、计划/目标确认；**工具结果正文不进入候选提取**；
- 每日 20 次调用、200k 输入 tokens；
- 输出必须通过 schema，置信度封顶 0.7；
- 连续 3 次失败熔断，成功一次复位。

代价是明确的：规则模式会漏掉需要归纳的结论；LLM 模式更贵，而且 0.7 的置信度上限意味着自动写入永远不是“高置信事实”。我们接受这个上限，因为让模型自动提升自己的可信度，比漏记一条更危险。

另一条负结论：**把记忆做成向量库并不划算**。记忆的预算是 2k tokens，条目数量有限，关键需求是“每次都出现”和“排序稳定”；向量检索解决的是“从大库里找相关项”，它既不保证常驻，又会引入模型文件和冷启动。这里用不上。

## 三、Wiki：页面是事实，索引是派生物

Wiki 的存储选择很朴素：一行 Markdown 一页，frontmatter 记录 `sources`、`confidence`、`status`、`revision`。索引、分块、BM25 都是派生物，删掉后可以从页面重建。

检索默认用 BM25，字段权重是 title 3×、tags 2×、heading 2×、body 1×，中文按 bigram 处理。没有默认上嵌入。不是不认可向量检索，而是这个项目里它带来的固定成本太高：模型文件 100–500 MB、冷启动、维度与版本迁移，以及“离线也要先装模型”的可用性负担。以万级块以内的规模，BM25 + 字段权重 + CJK bigram 已经够用；嵌入作为可选插件存在，不上就不改变行为。

预算同样写死：

| 参数 | 默认值 |
| --- | ---: |
| 检索条数 | 8 |
| 检索字符 | 6k |
| 检索超时 | 150ms |
| 常驻目录 | 1,200 字符 |

超时返回已检索到的部分并标 `truncated`，不阻塞回合。**预算比排序更能防止知识库挤爆上下文**：排序只决定谁排前面，预算决定最坏情况。

默认只常驻目录，正文靠模型调用 `wiki_search` / `wiki_read`。可选的 `@ruobai/wiki-automation` 提供了另一个开关：每轮用最新用户消息检索一次，把命中的摘要与片段注入 system 末尾（section 96，位于稳定前缀之后）。它默认关闭——每轮检索会多一次本地搜索，并让 system 尾部随轮次变化；打开它换的是“模型不用自己想起去搜”，代价是尾部缓存和少量噪声。

常驻目录不是所有页面，只有同时满足三个条件的页面才进入：`status = ready`、有来源、有摘要。其余页面只能通过检索发现。这个门槛经常被问“为什么不把所有页面列出来”——因为目录是每轮都发的，1,200 字符是硬上限；把草稿、未溯源、过期页面塞进去，等于用稀缺的常驻空间换低质量线索。

评估口径：以仓库 `docs/*.md` 为语料、20 条查询，Recall@5 = 19/20（0.95）。这是**召回**指标，不是答案正确率；它说明“相关页面在前五条里”基本成立，不说明页面本身没过期、没有冲突。后者要靠来源与审核，不靠检索分数。

## 四、写入：提案是缓冲带，不是自动摘要

这里需要纠正一个常见误解：**harness 不会在会话结束后自动把内容总结进 wiki。** 自动蒸馏只发生在长期记忆那一层；wiki 的写入必须有人或模型显式触发。

目前能产生提案的入口只有三个：

| 触发 | 谁发起 | 写入 |
| --- | --- | --- |
| `/wiki save [标题]` | 用户 | 摘录最后 20 条文本消息，生成草案 |
| `wiki_propose` 工具 | 模型（Agent / Goal 模式） | 模型起草的标题与正文 |
| `POST /api/wiki/proposals` | 宿主或脚本 | 外部传入的提案 |

`/wiki save` 并不调用模型做总结：它取会话最后 20 条文本消息，每条截断到 400 字，拼成“摘要 + 原始摘录”。这很粗糙，但它是**可预期的**：没有额外 token 成本，也不会把模型的一次即兴归纳伪装成项目事实。模型主动调用 `wiki_propose` 时才会真正起草正文，但它同样只写提案目录。

```text
会话 ──/wiki save──────▶ 摘录草案 ─┐
     └─wiki_propose────▶ 模型草案 ─┴─▶ .proposals/<id>.md
                                           │
                                     人工审核 │
                              ┌────────────┼────────────┐
                              ▼            ▼            ▼
                            接受        编辑后接受      拒绝
                              │            │            │
                              ▼            ▼            ▼
                    写 pages/ + 旧版本   提案内修改     删除提案
```

接受提案时才会写页面，并把旧版本留在历史里。UI 的提案视图默认显示**正文 diff**，可以切完整提案，也可以编辑后接受；“接受前不会修改页面”不是一句提示，而是路径上真的没有写 `pages/` 的分支。

模型还有一条更直接的路径：`wiki_write`。它直接写页面，但 `requiresApproval: true`，会走审批卡片和 diff 预览。设计上更推荐 `wiki_propose`，因为审批只解决“能不能写”，不解决“值不值得写”；提案把这两个判断分开了。

### 为什么默认不做自动提案

最直接的答案是：**知识库的价值在策展，不在把每个会话都变成一篇文章**。自动摘要的失败方式不是报错，而是缓慢堆积：同一结论出现五个版本、来源缺失、过期内容仍被检索、冲突被新文本覆盖。等到人发现时，清理成本比当初手写还高。

所以自动提案做成可选插件 `@ruobai/wiki-automation`，默认关闭。打开后由空闲触发：最后一轮结束 10 分钟、至少积累 2 个新用户回合，用当前非 mock 模型起草一页；每日 10 次 / 100k tokens，连续 3 次失败熔断。它仍然只写 `.proposals/`，接受前不会碰页面。

第二条原因是权限边界。Ask / Plan 模式只开放只读工具，`wiki_propose` 和 `wiki_write` 都不在工具白名单里；Agent / Goal 才提供。这不是遗漏，而是“不要让只读模式产生持久副作用”的一部分。

代价也要说清：**提案需要人看**。`/wiki save` 出来的草案通常不能直接接受，得补结论、核对来源、删掉会话里的临时上下文。这是有意的摩擦；如果这条摩擦消失，wiki 很快会退化成另一个聊天记录。

## 五、来源、过期与版本

wiki 和“文档 RAG”最大的区别不在检索，而在页面有来源。

每条 `sources` 记录 `kind`（file / session / url）和路径或会话 id；文件来源还会记录内容 hash。源文件变化或消失时，页面标记为 stale，但**不会自动改写**。理由很简单：源变了不等于结论错了，也可能只是文档重构；自动改写会把一次误判扩散到整页。

过期在 UI 上分成两层：

- 页面级 `status = stale`，检索降权，目录不收录；
- 来源级标记，指出具体是哪个文件缺失或变化。

冲突也不静默覆盖：新旧值都保留在 `## 冲突` 段里，双方来源都留着，由人或后续提案消解。页面详情会显示“冲突未消解”。

版本由写入路径负责。每次更新页面先保存旧版本；UI 可以查看某个历史版本，也可以和当前修订对比。diff 只比较正文，不比较 frontmatter——否则每次写入的时间戳都会出现在 diff 里，把真正的修改埋掉。

## 六、边界与没做的事

这套设计有几处明确的“不做”，它们和做了什么一样重要：

- **自动提案与自动检索默认关闭**。它们由 `@ruobai/wiki-automation` 提供：空闲 10 分钟后起草待审提案，或每轮按问题注入 ≤8 条检索结果。打开会多一次检索/模型调用，并改变 system 尾部。
- **没有默认向量检索**。BM25 的短板是语义近邻，长处是离线、可解释、索引可重建；当前规模下先接受这个短板。
- **没有自动修复过期页面**。只标记，不改写。
- **没有把 wiki 当作规则系统**。必须每次生效的约束仍然属于 `AGENTS.md`；wiki 是“可查阅的知识”，不是“必然执行的指令”。
- **记忆与 wiki 不会自动互相引用**。一条事实可以既在记忆里有一句摘要、又在 wiki 里有完整页面，但需要人决定；自动交叉引用很容易制造两份互相矛盾的事实。

还有一个运营上的边界：检索 Recall@5 = 0.95 意味着仍有 5% 的查询在 top-5 里找不到目标页。它可以通过更好的标题、摘要和标签改善，但不能靠调大 top-k 解决——预算会先撑不住。

## 收束

把记忆和 wiki 放在一起看，真正起作用的不是“知识库”这个词，而是两条不同的约束：

- **记忆靠预算和确定性活着**：≤ 2k tokens、固定优先级、字节稳定的快照。它的敌人是膨胀和漂移。
- **wiki 靠来源和审核活着**：页面是事实、索引是派生、提案是缓冲带。它的敌人是自动堆积和过期。

所以这不是“一个大库切成两层”，而是两种知识生命周期的分工：**该每次出现的，接受被裁剪；该按需查的，接受被审核。**

## 术语表

| 术语 | 解释 |
| --- | --- |
| LLM Wiki | 由人和模型共同维护的 Markdown 页面集合，索引可重建、页面可审核。 |
| journal | 记忆的只追加事件日志，是记忆的唯一事实来源。 |
| 快照 / 注入块 | 由 journal 确定性编译出的 `MEMORY.md` 与每轮注入内容。 |
| 注入预算 | 每轮允许进入 system prompt 的记忆 token 上限，默认合计 2,000。 |
| 蒸馏 | 从会话提交边界抽取记忆候选；默认规则抽取，LLM 模式需显式开启。 |
| frontmatter | 页面顶部的元数据段，记录 id、标题、标签、来源、置信度、状态与修订号。 |
| 提案（proposal） | 写在 `.proposals/` 下的页面草案，接受前不影响 wiki。 |
| 目录（catalog） | 常驻 system 的页面摘要列表，≤ 1,200 字符，只收 ready、已溯源、有摘要的页面。 |
| stale | 页面来源文件缺失或 hash 变化；只标记，不自动改写。 |
| BM25 | 词法检索打分函数；这里配合 CJK bigram 和字段权重使用。 |
| Recall@5 | 前五条检索结果中包含目标页面的查询比例；本文口径为 20 条查询命中 19 条。 |

设计细节与失败模式见 [docs/memory-and-wiki.md](../memory-and-wiki.md)。
