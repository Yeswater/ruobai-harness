# 写 ruobai-harness 博客

博客不是设计文档，也不是发布说明。设计文档回答"问题、约束、方案、失败模式、验证"；博客回答**"当时怎么判断、放弃了什么、为什么"**。同一件事可以两边都写，但不要互相抄。

## 0. 先定一句主张

动笔前先写出这句话，写不出就说明还没想清楚：

- 好：**把历史当接口，只追加不改写。**
- 坏：**我们优化了 KV cache 的交互。**

前者是判断，能推出每一节该写什么；后者是事件，只会写成流水账。正文每一节都要服务于这句主张，服务不了就删。

## 1. 证据：数字必须能复现

- **先定口径，再给数**。命中率、成本、延迟都要写清"怎么算的、单位是什么、`1.0` 代表什么"。
- **用仓库真实代码做 A/B**，不要凭感觉估。旧行为可以用等价方式复现（例如用一个等价日志事件模拟旧策略），但要在文中说明这是复现。
- **区分上界与实测**。字符级前缀是上界、token 块会向下取整、估算器是启发式——都写明。
- **主动给负结论**。"把摘要从 system 搬到 messages 并不省缓存"这类结论和正结论一样有价值。
- 数字进表格，判断进正文。**不要用正文复述表格里的百分比。**
- 至少留一条"代价"：这个改动让什么变差了、谁需要承担。

## 2. 结构

- 文件名：`docs/blog/YYYY-MM-DD-中文标题.md`，日期 + 中文标题。
- 开头三件套：一级标题、`> 日期 · ruobai-harness`、一段话讲清"这篇回答什么问题、结论是什么"。
- 主体按**论证**推进，不按时间推进：问题 → 证据 → 方案与取舍 → 边界。不要从"第一天我们……"开始。
- 用户点名了框架再套框架（如 SMART）；没点名就不要硬套。
- 结尾收在一句话主张，或一张取舍清单。
- 长度与 `docs/blog/` 既有文章相当（约 8–15KB）。超了先删，不要扩。

## 3. 删：流水账清单

出现下面任何一项，就还没写完：

- 阶段表（阶段 0–4 完成情况）、文件清单、提交历史；
- "我们做了 A，然后做了 B"的顺序叙述；
- 表格已经给出的数字，正文再讲一遍；
- 形容词与副词（"显著提升""大幅优化"）——能量化就用数，不能量化就删；
- 每段都问一句：**删掉它，主张会受损吗？** 不会就删。

## 4. 配图：只在能替代一段解释时加

- 多组对比 → `xychart-beta` 条形图；判定规则 → `flowchart TD`。
- 结构示意如果 ASCII 已经清楚，**保留 ASCII**（终端、GitHub、纯文本编辑器都能看）；换成 Mermaid 只在它能表达更多关系时做。
- Mermaid 约定：
  - 中文标签一律加引号：`x-axis ["旧·工具循环", "新·工具循环"]`、`B{"上下文 ≥ 阈值?"}`；
  - 不写死颜色，跟随应用主题；
  - 图上不要放正文已经说过的结论。
- **验证方式**：起 `pnpm dev`，用应用里的文件面板打开这篇 md（`FileBrowser` 与聊天共用 `MarkdownPreview`），确认 `.mermaid-block` 生成了 SVG 且没有 `.mermaid-error`。不要只看 Markdown 源码。

## 5. 术语表

- 放在文末，**只收正文实际用到的词**；没出现的词不要为了"完整"加。
- 一行一条，给最小定义，不展开历史。
- 正文首次出现时仍要给一个最短解释，别让读者必须跳到文末才能读懂。

## 6. 交付前检查

- [ ] 能用一句话说出主张，且它出现在开头或结尾
- [ ] 每个数字都有口径、来源与边界
- [ ] 至少一条负结论或明确的代价
- [ ] 没有阶段表、文件清单、提交历史
- [ ] 表格给数，正文给判断，没有重复复述
- [ ] 配图都能替代一段文字，且已在应用里渲染验证
- [ ] 术语表只含正文用到的词
- [ ] 与设计文档交叉引用（`docs/<topic>.md`），但没有整段复制
- [ ] 长度在 8–15KB

## 7. 参考

- 仓库约定：`AGENTS.md` §9「文档与提交」。
